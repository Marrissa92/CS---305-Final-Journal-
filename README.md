### 1. Briefly summarize your client, Artemis Financial, and its software requirements. Who was the client? What issue did the company want you to address?
* **Answer:** Our client was **Artemis Financial**, a financial services institution responsible for protecting highly sensitive consumer assets, including personal investments, savings accounts, and retirement portfolios. The primary issue the company wanted addressed was securing their web application against active data breaches, unauthorized intercepts, and external exploits. Given the international nature of their data transfers, the software required strict alignment with global security standards like **GDPR** and federal privacy mandates like the **Gramm-Leach-Bliley Act (GLBA)** to preserve data confidentiality and integrity. 

### 2. What did you do well when you found your client’s software security vulnerabilities? Why is it important to code securely? What value does software security add to a company’s overall well-being?
* **Answer:** We did a great job combining thorough manual line-by-line code reviews with automated static analysis scanning to flag outdated, highly vulnerable software packages—specifically identifying critical vulnerabilities like *Spring4Shell* (**CVE-2022-22965**), Jackson Data Overload (**CVE-2020-36518**), and Spring Boot Exposure (**CVE-2021-22096**). Proactively coding securely from the very start is crucial because finding and fixing a logic gap early saves immense engineering time, development costs, and operational overhead before code goes live. For a business, strong software security directly protects consumer trust, shields the brand from massive financial or legal liabilities, and ensures they pass compliance audits cleanly. 

### 3. Which part of the vulnerability assessment was challenging or helpful to you?
* **Answer:** Running the automated **OWASP Dependency-Check plugin** within our workspace was incredibly helpful because it instantly mapped out and pinpointed known third-party software flaws that would be nearly impossible to find through manual inspection alone. The most challenging part was dealing with nested, transitive dependencies and tracking down exactly which parent or background library was pulling hidden risks into the application's runtime path. Balancing automated scan data with a manual verification walk-through really helped map out an actionable blueprint of the system's weaknesses. 

### 4. How did you increase layers of security? In the future, what would you use to assess vulnerabilities and decide which mitigation techniques to use?
* **Answer:** We increased layers of security by immediately updating our project configuration file (`pom.xml`) to upgrade the core parent frameworks to active, stable, and secure releases, which instantly resolved over 90% of our active vulnerable dependencies. We also established immediate, short-term plans to harden system settings—such as locking down unprotected internal monitoring screens behind robust password gates and creating strict validation filters for text entry boxes. In the future, I plan to integrate automated security scanning tools directly into the team's continuous integration and continuous deployment (**CI/CD**) pipeline to assess vulnerabilities on every single code commit before they enter a production environment.
  
### 5. How did you make certain the code and software application were functional and secure? After refactoring the code, how did you check to see whether you introduced new vulnerabilities?
* **Answer:** We made certain the application remained fully functional by executing the project build tools locally, observing the startup console logs, and confirming that the embedded web server initialized cleanly without breaking any core application features. After refactoring and upgrading the baseline frameworks, we reran our automated vulnerability check against the revised codebase. This verified that the high-severity security flaws were thoroughly eliminated and confirmed that the upgrades had not introduced any new conflicting vulnerabilities or code regressions. 

### 6. What resources, tools, or coding practices did you use that might be helpful in future assignments or tasks?
* **Answer:** Utilizing automated static application security testing (SAST) tools, like the **OWASP Dependency-Check tool**, was a powerful asset that will definitely be useful in future projects. Practicing defensive coding techniques—such as validating inputs to block rogue text blocks and enforcing encrypted communication paths (HTTPS over HTTP)—are vital baseline safety practices that can be applied to any software project. Additionally, keeping up with regular dependency maintenance and monitoring framework support lifecycles will be a standard practice moving forward.
